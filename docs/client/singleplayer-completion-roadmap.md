# 单人赛事完整模式开发路线

版本：0.1

目标：在现有第一切片基础上，完成从基础牌组开始，经历多轮构筑、配对、战斗和赛事生命结算，直到决出胜者的本地单人模式。

## 当前基线

已完成：

- 四名参赛者、初始八张基础牌和赛事生命；
- 构筑前公布第一轮固定配对；
- 共享候选库存、购买、跳过、结束构筑和 AI 构筑；
- 战斗实例管理、同步行动、基础元素层效果；
- 战后赛事生命结算；
- Godot 场景、纯色占位资源和固定种子回归测试。

固定基线不能被后续功能悄悄改变：卡牌数据、构筑规则、伤害公式和事件序列必须通过版本化测试更新。

## 实施顺序

### 1. 扩展赛事状态

在 `MatchState` 增加：

- 当前轮次和赛事阶段；
- 每名玩家的存活、淘汰轮次和连胜/连败信息；
- 已完成对局集合和历史配对集合；
- 下一轮研习点增量；
- 淘汰玩家的幽灵快照。

保持 `TournamentLife` 与 `CombatState.Life` 分离。所有字段都进入 `StateHasher` 和快照 DTO。

验收：保存并恢复赛事后，状态哈希、随机流和当前阶段完全一致。

### 2. 建立多轮阶段状态机

固定状态流：

```text
Setup
  -> PairingPublished
  -> Draft
  -> Combat
  -> Settlement
  -> NextRound / Finished
```

每个阶段只接受该阶段命令。配对必须在构筑开始前发布，结算完成后才能进入下一轮。

建议新增：

- `RoundCoordinator`：驱动轮次转换；
- `RoundStartedEvent`；
- `SettlementStartedEvent`；
- `NextRoundStartedEvent`；
- `TournamentFinishedEvent`。

### 3. 完整化每轮构筑

按冻结构筑规则逐项接入，不直接改写现有 `MatchCoordinator`：

1. 共享池候选生成与库存预留；
2. 购买、跳过和结束时的库存回收；
3. 每轮刷新次数和刷新费用；
4. 删除/替换牌的回池处理；
5. 专精即时赠卡与已有附魔收益更新；
6. 路线选择、替换和全场公开事件；
7. 淘汰玩家停止购买；
8. 连胜/连败奖励研习点。

每一步都使用命令处理器，AI 与玩家不能直接修改牌组或库存。

### 4. 实现多轮配对服务

将第一轮固定配对替换为可复现的 `IPairingService`：

- 优先避免上一轮和近期重复对战；
- 活人优先配对；
- 不足时使用淘汰玩家的幽灵快照；
- 保留双死、并列和最后同时全灭情况；
- 同一种子得到相同配对顺序。

配对结果写入 `PairingsPublishedEvent`，客户端只显示公开配对结果。

### 5. 建立轮次牌组快照

构筑完成后，为每场对局生成不可变牌组快照：

- 牌实体 ID 保持唯一；
- 战斗实例使用快照，不引用可变的玩家牌组；
- 断线、回放和重播都从快照重建；
- 同一轮的两场战斗使用独立随机流。

现有 `BattleInstanceManager` 继续作为战斗实例边界，不让 UI 直接创建 `CombatState`。

### 6. 完成战斗客户端操作

在 `CombatBoard` 增加：

- 当前手牌和费用显示；
- 出牌、检索目标和结束窗口操作；
- 双方生命、护盾、攻击、防御和元素层公开信息；
- 战斗事件日志；
- 跳过动画后直接应用最终状态；
- 玩家对局和 AI 对局的顺序展示。

玩家和 AI 都通过 `BattleInstanceManager.Submit` 提交命令。客户端不能提交伤害、胜者或赛事扣血结果。

### 7. 接入完整战斗 AI

新增 `Slice1CombatController`：

- 为每个 AI 创建独立策略实例；
- 只提供自己的完整状态、对手公开状态和合法检索候选；
- 每次行动使用战斗修订号；
- 非法或过期命令自动拒绝并重新决策；
- 记录决策原因用于回放，不向玩家泄露私有牌组。

### 8. 实现战后结算和淘汰

按冻结规则实现：

- 使用 `m + floor(ln(max(x,1)) * n)`；
- 双死只扣基础值 `m`；
- 赛事生命降至 0 时标记淘汰；
- 淘汰玩家的牌组和未购买候选按规则回池；
- 生成幽灵快照供后续轮次配对；
- 结算完成后统一发布存活者和淘汰者事件。

结算必须幂等：同一战斗结果重复提交不能重复扣血。

### 9. 实现胜者判定

每轮结束后：

- 若多名活人存在，生成下一轮构筑；
- 若只剩一名活人，进入胜利结算；
- 若最后一场发生同时全灭，沿用并列冠军规则；
- 不因 UI 顺序提前截断赛事。

新增 `MatchResults.tscn`，显示每轮配对、战斗胜负、扣血、淘汰和最终冠军。

### 10. 连接客户端流程

`GameSession` 只负责生命周期和依赖注入，新增：

- `StartTournament(seed)`；
- `BeginNextRound()`；
- `EnsureBattleInstances()`；
- `ApplyFinishedBattles()`；
- `RestartTournament(seed)`。

场景职责保持清晰：

- `Boot`：加载冻结数据并创建会话；
- `Match`：阶段路由和公共赛事信息；
- `DraftBoard`：构筑命令和牌组视图；
- `CombatBoard`：战斗命令和战斗事件；
- `MatchResults`：轮次结算和冠军结果。

### 11. 固定种子回归测试矩阵

每次规则或客户端更新必须运行：

1. 初始四人和八张基础牌；
2. 候选库存守恒；
3. 同名牌限制和允许重复基础牌；
4. 配对不重复和幽灵快照；
5. 双方同步战斗行动；
6. 基础伤害、护盾、元素层和疲劳；
7. 每轮扣血、淘汰和双死；
8. 多轮状态哈希；
9. 最终胜者或并列冠军；
10. 同一种子双次回放完全一致。

每个固定种子都保存最终状态哈希和事件日志摘要。哈希变化必须伴随规则版本或测试基线更新。

### 12. 打包和启动入口

完成可玩闭环后：

- 生成独立调试包和发布包；
- 快捷方式始终指向当前发布入口；
- 每次客户端更新后重新生成桌面快捷方式；
- 快捷方式工作目录固定为项目或发布包目录；
- 发布包启动前运行一次固定种子验收。

## 推荐里程碑

```text
M1 多轮状态和阶段机
M2 多轮构筑与共享池回收
M3 多轮配对和牌组快照
M4 战斗客户端完整操作
M5 淘汰、幽灵和胜者判定
M6 固定种子全赛事回归
M7 发布包和快捷方式自动更新
```

每个里程碑都必须同时通过核心测试、无头回归和 Godot 场景启动测试，再进入下一阶段。
